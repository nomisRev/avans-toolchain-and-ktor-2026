# Executed code is not necessarily tested well

```kotlin
@Test
fun createsAnOrder() {
  orders.create(OrderRequest(productId = 42))
  // The code ran. What behavior did we actually assert?
}
```

Coverage reveals gaps. Assertions establish expectations.

Use the report to ask about error paths and boundary cases.

- Kotlin/JVM coverage with Kotlin-aware filtering
- Gradle reports, aggregation and verification
- A standalone JVM agent and CLI when Gradle is absent

JaCoCo remains a practical option, especially through the Maven bridge.

# Kover: reports and a gate in Gradle

```kts gradle
plugins {
  id("org.jetbrains.kotlinx.kover") version "0.9.8"
}

kover {
  reports {
    total {
      verify {
        rule { minBound(80) }
      }
    }
  }
}
```

```bash
./gradlew koverHtmlReport koverXmlReport koverVerify
```

<!--
Assumes Kotlin/JVM and test setup already exist. Version 0.9.8 matches the inspected Ktor project and official guide. minBound uses covered line percentage by default; 80 is an example policy. Call koverVerify explicitly in CI rather than assuming applying a plugin enforces the intended threshold.
The Gradle integration wires relevant tests into reporting. For multiple modules, configure aggregation explicitly; a root plugin alone does not imply all subprojects are included.
-->

# Kover also works without Gradle

```bash
# Pinned agent; keep its original filename
mkdir -p reports/coverage
cat > reports/coverage/agent.args <<EOF_ARGS
report.file=$PWD/reports/coverage/backend.ic
report.append=false
EOF_ARGS

AGENT="$PWD/tools/kover-jvm-agent-0.9.8.jar"
ARGS="$PWD/reports/coverage/agent.args"
./kotlin test -m backend --jvm-args \
  "-javaagent:$AGENT=file:$ARGS"
```

The agent instruments the **test JVM**, then writes execution data.

<div class="source"><a href="https://kotlin.github.io/kotlinx-kover/jvm-agent/">Kover agent configuration</a></div>

<!--
Example assumes one module, one writer and paths without spaces. Provision compatible pinned agent/CLI jars separately. Kover agent documentation specifically says not to rename the agent jar. It uses a settings file, not JaCoCo's comma-separated options. Each test shard needs a separate report; report.append=false would otherwise overwrite preceding execution.
This is an alternative to JaCoCo instrumentation, not a second agent to stack onto the same test run. The student's exact project has not been executed.

# Turn execution data into a report

```bash
java -jar tools/kover-cli-0.9.8.jar report \
  reports/coverage/backend.ic \
  --classfiles "$BACKEND_CLASSES" \
  --src backend/src \
  --html reports/coverage/html \
  --xml reports/coverage/report.xml
```

Use the matching original production classes and source roots.

The CLI report still needs a separate threshold verification step.

<div class="source"><a href="https://kotlin.github.io/kotlinx-kover/cli/">Kover CLI report and merge commands</a></div>

<!--
BACKEND_CLASSES is an explicit validated path supplied by the script/build integration. Include all production roots in scope; don't mix test classes or stale output. Repeat supported options for additional roots. Don't rebuild classes between execution and reporting.
Kover CLI does not expose the Gradle koverVerify task. Read report-level XML counters with a small verifier, or choose an integration with verification support. Fail on missing execution data, missing reports or empty measurable scope. Merge per-shard .ic files with the CLI merge command if needed. Kover .ic and JaCoCo .exec are not interchangeable.

# Separate measurement from policy

```text
Measure:     Which production lines executed?
Report:      Show the gaps in HTML / XML
Verify:      Fail below the agreed minimum
```

Agree the scope, exclusions and threshold before enforcing it.

Missing or empty data should fail, not quietly pass.

<!--
80% on the Gradle slide is illustrative, not prescribed. Coverage thresholds should focus discussion on behavior and protect against regressions. Prefer explicit exclusions for generated code over broad package exclusions that hide business logic.
If implementing XML verification, read the top-level LINE counter once; summing nested counters double-counts. covered/(covered+missed), with a deliberate zero-denominator policy. JaCoCo CLI, like the shown Kover CLI route, creates reports without automatically enforcing a gate.
-->

# Avoid coupling CI to internal output paths

```text
build/artifacts/CompiledJvmArtifact/
  <module>jvm/kotlin-output/
```

No stability guarantee found for this layout.

Prefer build-model inputs; otherwise isolate and validate the path.
